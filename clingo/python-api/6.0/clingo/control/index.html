clingo.control ¶

Module containing the Control class responsible for grounding and solving.

Example¶

The example shows the most straightforward way to ground and solve a small test program:

>>> from clingo.core import Library
>>> from clingo.control import Control
>>>
>>> lib = Library()
>>> ctl = Control(lib)
>>> ctl.parse_string("1 { a; b }.")
>>> ctl.ground()
>>> print(ctl.solve(on_model=print))
a
SAT

profile property ¶

profile: list[dict[str, Any]]

Get the profiling information as a list of profile nodes.

Profiling data is only collected if profiling is enabled via the --profile option. Otherwise, the list is empty.

Each node is a dictionary. Internal nodes have the keys "type" ("internal"), "key", "nested", and "children". The key is the string representation of an expression in the logic program, nested indicates whether the node's times are already included in its parent node, and children is the list of child nodes. Leaf nodes have the keys "type" ("leaf"), "profile_type" ("step" for the last step or "accu" for all steps), "matches", "instances", "time_instantiate", and "time_propagate", where the times are given in nanoseconds.

The result is directly convertible to JSON using Python's json module.

main ¶

main() -> None

Ground and solve a logic program based on the current control mode.

This function serves as a high-level entry point for the default ground-and-solve process. It proceeds as follows:

  1. If a script defines a main function, execution is dispatched to it.
  2. Otherwise, in ControlMode.Parse and ControlMode.Rewrite, the parsed or rewritten program is printed.
  3. Otherwise, if the program includes <incmode>, incremental grounding and solving is performed.
  4. Otherwise, the program parts in parts (or the base part if none are set) are grounded, followed by a single solve call in ControlMode.Solve.

Before calling main(), the control object can be prepared by parsing programs, registering propagators, or performing other setup steps.

Solve the current ground program in the background and return an awaitable handle.

Awaiting the handle returns the solve result. With yield_=True, the models can be iterated with async for before awaiting the result. Otherwise, models can be intercepted with the on_model callback.

start_solve ¶

start_solve(
    assumptions: Sequence[tuple[Symbol, bool] | int] = [],
    on_model: Callable[[Model], bool | None] | None = None,
    on_unsat: Callable[[Sequence[int]], None] | None = None,
    on_stats: Callable[[Stats, Stats], None] | None = None,
    on_finish: Callable[[SolveResult], None] | None = None,
    yield_: bool = False,
    async_: bool = False,
) -> SolveHandle

Start solving the current ground program.

This function runs the solver on the current ground program, optionally using assumptions, callbacks, or asynchronous execution. It returns a SolveHandle, allowing interaction with the solving process.

If asynchronous solving (async_) is enabled, the function returns immediately, and solving runs in the background. Otherwise, if yielding (yield_) is enabled, models are computed one at a time when they are requested via the handle. If neither is enabled, the function blocks until solving is complete.

Parameters:

Name Type Description Default
assumptions Sequence[tuple[Symbol, bool] | int]

The assumptions that constrain the search. Each assumption is either a tuple[clingo.symbol.Symbol, bool] indicating an atom's truth value or a program literal (see literal). For example, using [(clingo.symbol.Function(lib, "a"), True)] only admits answer sets that contain atom a.

 []
on_model Callable[[Model], bool | None] | None

An optional callback that receives a Model object when a model is found. Returning False from the callback stops solving.

 None
on_unsat Callable[[Sequence[int]], None] | None

An optional callback to intercept lower bounds during optimization.

 None
on_stats Callable[[Stats, Stats], None] | None

An optional callback that receives statistics updates after each step. Two Stats objects are passed: the step-specific and the accumulated stats.

 None
on_finish Callable[[SolveResult], None] | None

An optional callback called once the search has finished. A SolveResult is passed to the callback.

 None
yield_ bool

If True, the returned SolveHandle is iterable, yielding Model objects during solving.

 False
async_ bool

If True, solving runs asynchronously in a separate thread. Callbacks (on_model, on_stats, etc.) are then also called from a separate thread.

 False

Returns:

Type Description
SolveHandle

A handle to control the search.
Notes

Asynchronous solving requires compiling clingo with thread support. Blocking methods on SolveHandle release the GIL but are not thread-safe.

write_aspif ¶

write_aspif(
    path: str | None = None,
    symbols: bool = False,
    append: bool = False,
    preamble: bool | None = None,
    preprocess: bool = True,
) -> None

Write the current logic program in aspif format.

If path is None, the program is written to clingo's internal output buffer, which is available via buffer. Otherwise, it is written to the given file, which is created if it does not exist.

If append is false, an existing file is overwritten. Output to the buffer is always appended to its current content.

If preamble is None, the aspif preamble is written unless the program is appended to existing content, i.e., unless append is true and the file exists or the buffer is non-empty. In application mode, the buffer is printed to stdout and cleared after each major operation like grounding, so the preamble flag should be set explicitly in this case.

Parameters:

Name Type Description Default
path str | None

The optional path to write the program to.

 None
symbols bool

Whether to also write the symbols of the program.

 False
append bool

Whether to append to existing content.

 False
preamble bool | None

Whether to write the aspif preamble.

 None
preprocess bool

Whether to preprocess the program before writing.

 True
